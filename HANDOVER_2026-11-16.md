## 4. Security findings

Proved by `tests/main/entry-security-stress.ts` (new, 21.2 s, all assertions green):

- SQL-injection literals pushed through the real repositories (`'; DROP TABLE products;--`,
  `UNION SELECT`, quote/backslash payloads) are stored as data and never executed; the tables
  survive and the integrity check stays clean.
- Hostile search input (wildcards, `%`, `_`, quotes, control characters) matches literally.
- Passwords are stored salted and hashed — the plaintext never appears in the users table.
- A session token is genuinely refused after logout (403/401, not "ignored").
- `PRAGMA foreign_keys` is really ON for the app's connection; a bad FK insert is rejected by
  SQLite itself; the manual cascade deletes children and leaves no orphans.
- A 300-product / 300-customer / 150-order dataset loads through the IPC data layer and
  `checkDatabaseIntegrity()` reports no violations.
- Cross-workspace isolation is covered by `entry-worker-tenant-isolation` (12/12 assertions):
  Company A's list contains only A's users, A's owner cannot authenticate into B, a forged
  `x-user` sender is rejected, `x-workspace-id` is ignored once a Bearer session exists, and
  the Employee→Employee message block holds server-side.

**Unresolved (F47, High):** every Worker request re-derives the workspace API key with
`scrypt(N=16384, r=8, p=1)` in `resolveWorkspaceForApiKey()`. That is correct for storage but
puts one scrypt per request in front of every sync call — measured at ~800 ms/request on a busy
machine, against Cloudflare Workers' per-request CPU limit (10 ms free / 30 s paid). Recommended
fix (not applied, it is an auth-design change): cache the verified key per isolate, or store a
keyed HMAC of the key instead of a scrypt hash. This should be resolved before a production
launch with many workspaces.

**Also noted, not security:** `entry-worker-tenant-isolation` still asserts that reusing a
username across workspaces returns a clean 409 — i.e. `users.username` remains globally unique
until migration `0003_workspace_unique_constraints.sql` is applied to the real D1 database. The
migration ships in `cloudflare/migrations/`; applying it is a deployment step.

## 5. Performance findings

- The app is not the slow part of cloud sync — the Worker's per-request key verification is
  (see F47). A plain-Node loopback control does 20 requests in 65 ms; the same sync spends
  ~800 ms per request because each one pays a scrypt.
- The two cloud entries are therefore CPU-bound, not hung or deadlocked. The runner bound is
  600 s with the measurement recorded in `scripts/run-main-tests.mjs`; `MBS_SYNC_TRACE=1` prints
  per-phase timings (`syncOnce`) when this needs to be re-measured.
- Local data-path operations stayed in the single-digit-millisecond range across the whole
  suite (order/invoice create + invoice regeneration: 44.7 s for the entry's ~157 orders and
  22 invoices, including seeding and assertions).
- **No production-scale performance number exists for this build.** The brief's 50k customers /
  200k orders / 1M ledger rows was not generated; do not quote any figure from this pass as one.

## 7. Limitations — what was NOT done

1. **No installer install on a clean machine.** The NSIS installer is built and its contents are
   verified, but installing it on a fresh Windows profile and walking first launch was not done.
   It is also **unsigned** — SmartScreen will warn.
2. **Nothing was deployed.** Cloud behaviour was proved against the shipped Worker code running
   in-process (real HTTP server + D1 shim); `wrangler deploy`, the production D1 database and the
   live domain were not exercised.
3. **Not production-scale load testing** (see §5).
4. **No full-path penetration test**: path traversal under real file writes, XSS/XLSX-formula
   payloads, brute-force timing and a secret grep over the installer remain untested.
5. **Human-error clicking** is partly covered (empty submits, Escape/Tab, dialog dismissal);
   double-submit and offline-transition behaviour are not.
6. **Only one of the module/settings pages was redesigned** (`financial-invoice`); the other 10
   modules and 18 settings subpages inherit the tokens and render correctly but were not
   re-authored page by page.
7. **Screenshot matrix is not exhaustive**: 30 routes at one canonical size + 7 routes ×
   2 sizes × 3 languages × 2 themes; the full 18-combination sweep for every route was not run.
8. **Cloud sync is slow by design at the auth layer (F47)** and this pass deliberately did not
   change it.
9. The light-theme window flash at startup persists: the theme lives in the renderer's
   `localStorage`, so the BrowserWindow paints before the renderer applies it.

## 8. Release verdict

**Ready for internal / pilot use. Not yet cleared for a wide production rollout.**

Green: typecheck, build, 12/12 main entries (296 assertions), 6/6 e2e, release verification,
online architecture verification, signing-config check, installer build, 199-shot screenshot
sweep with 0 renderer errors, interaction pass with 0 native dialogs, happy-path write path with
0 failed assertions.

Two things stand between this build and a production launch, and neither is a code regression:

1. **F47** — per-request `scrypt` API-key verification on every Worker call. Fix the auth hot
   path before traffic grows (isolate-level cache or HMAC-compare stored key).
2. **Deployment steps** — apply `0003_workspace_unique_constraints.sql` to the production D1
   (removes the cross-workspace username conflict), deploy the Worker, and sign the installer.

Everything else outstanding is coverage, not defects: production-scale load, a real penetration
test, the remaining page-by-page redesigns, the full screenshot matrix, and a clean-machine
install test.
